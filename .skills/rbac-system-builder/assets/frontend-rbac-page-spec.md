# RBAC 前端页面规格

> 本规格用于把 RBAC 管理页从“功能清单”落到可实现页面。生成或改造前端时，先按目标项目的路由、API 客户端、组件库和权限模型适配本规格；不得新增第二套登录态或第二身份源。

## 一、信息架构

RBAC 管理区至少包含 6 个入口：

| 入口 | 目标用户任务 | 推荐页面形态 |
|---|---|---|
| 角色管理 | 创建、维护角色，查看角色成员和授权摘要 | 列表 + 详情抽屉 |
| 用户组管理 | 创建、维护用户组，查看成员和授权摘要 | 列表 + 详情抽屉 |
| 人员分配 | 从人员出发，批量分配角色或用户组 | 搜索列表 + 批量选择面板 |
| 成员管理 | 从角色/用户组出发，批量添加或移除人员 | 详情页 + 穿梭选择器 |
| 功能授权 | 给角色配置菜单、页面、按钮、API 权限 | 资源树 + 权限矩阵 |
| 数据权限 | 配置“我的数据”“我管理部门的数据”“指定部门数据”“分享某人的数据权限给某人” | 模板向导 + 预览 |

字段授权可作为“功能授权”的子页或独立入口；如果目标系统字段权限复杂，应独立成页。

## 二、通用交互规则

1. **最小授权默认值**：新建角色、用户组默认不授予高风险权限；保存授权前必须显式勾选。
2. **双向入口**：成员关系必须同时支持“人员 -> 角色/用户组”和“角色/用户组 -> 人员”。
3. **批量变更预览**：批量保存前展示新增、保留、移除、重复、冲突和无效项数量；保存后展示成功和失败明细。
4. **高风险确认**：删除/退休角色、删除/退休用户组、清空成员、批量移除成员、授予高风险权限必须二次确认并展示影响范围。
5. **业务化文案**：页面主交互使用业务名称，不用内部主键、策略 DSL、SQL、PIP 参数名作为主要输入。
6. **长 ID 安全**：用户、组织、岗位、角色、用户组、资源 ID 在前端均按字符串处理，不得使用 `Number()`、`parseInt()` 或一元 `+`。
7. **后端生效**：前端隐藏和禁用只是交互表现，功能权限、字段权限、行数据权限必须由后端真实执行。

## 三、页面规格

### 1. 角色管理

**路由建议**：`/rbac/roles`

**列表字段**：角色名称、角色编码、状态、成员数、功能权限数、数据权限数、更新时间、操作。

**筛选项**：关键词、状态、创建来源、是否有关联成员、是否有高风险权限。

**操作**：创建、编辑、退休/删除、查看成员、配置功能授权、配置数据权限。

**详情抽屉**：基础信息、成员摘要、功能授权摘要、字段授权摘要、数据权限摘要、审计信息。

**验收**：创建/编辑真实调用 AuthzCraft 角色接口或业务侧代理接口；删除/退休前展示成员数和授权影响范围。

### 2. 用户组管理

**路由建议**：`/rbac/groups`

**列表字段**：用户组名称、用户组编码、状态、成员数、关联角色数、更新时间、操作。

**筛选项**：关键词、状态、创建来源、是否有成员、是否参与数据权限策略。

**操作**：创建、编辑、退休/删除、查看成员、批量添加人员、配置数据权限。

**验收**：用户组 CRUD 真实调用 AuthzCraft 用户组接口或业务侧代理接口；成员数和关联授权在保存后回显正确。

### 3. 人员分配

**路由建议**：`/rbac/principal-assignments`

**主流程**：

1. 搜索并选择一个或多个人员。
2. 选择要分配的角色或用户组。
3. 展示已有关联、将新增关联、重复关联、冲突项。
4. 确认后批量保存。
5. 展示成功和失败明细。

**交互要求**：支持按部门、岗位、关键词筛选人员；支持批量选择、跨页已选保留、移除已选；已分配项必须清晰标记。

**验收**：同一人员可一次分配多个角色或用户组；重复分配不会生成重复成员关系；失败项可定位到具体人员和目标角色/用户组。

### 4. 成员管理

**路由建议**：`/rbac/memberships`

**主流程**：

1. 选择一个角色或用户组。
2. 查看当前成员列表。
3. 批量添加或移除人员。
4. 保存前预览新增、保留、移除差异。
5. 保存后刷新成员列表和成员数。

**交互要求**：推荐使用穿梭选择器或左右分栏选择面板；支持搜索、分页、已选去重和只看变更。

**验收**：可从角色/用户组维度批量添加人员；清空成员必须二次确认并展示影响范围。

### 5. 功能授权

**路由建议**：`/rbac/function-permissions`

**页面形态**：权限资源树 + 权限矩阵。**分组维度对齐业务导航心智**：权限分组 MUST 与前端菜单/导航/业务域对齐，而不是后端技术维度（资源表、表名、API 分组）。具体分组键由探查目标业务确定。

**展示文案**：操作权限 checkbox 只显示业务名称（如"查看报销单"），不拼接技术标识（权限 URN、code、resourceKey）。`name · code` 视为反例。

**必备能力**：搜索权限点、按模块折叠、全选/半选、只看已授权、只看变更、高风险权限标识、保存前差异预览。

**保存语义**：保存角色与权限点的最终集合或增量变更，具体按目标后端 API 约定；权限点编码必须与后端 `permissionCode` 逐字一致。

**验收**：保存后刷新当前用户权限或重新登录，菜单、按钮、API 访问结果与授权一致；无功能权限时后端返回 403。

### 6. 字段授权（两维模型）

**路由建议**：`/rbac/field-permissions`

**配置维度**：授权目标（角色/用户组/人员）、数据表、字段、访问级别（access_level）。

**两维模型**：`security_requirement`（字段固有属性，PLAIN/MASKED/HIDDEN）× `access_level`（授权可变属性，NONE/READ/PLAIN_READ/WRITE）。同一字段只有一种 `security_requirement`，权威来源是 AuthzCraft 回路 2 字段目录 `authzcraft_resource_field`，运行期 RBAC 管理页不得修改；授权时只选 `access_level`（单选，含"无权限"档）。

**列表语义**：字段授权页只显示当前授权目标已经绑定或本次待保存绑定的字段，按数据表分组（折叠面板）；不得显示全局所有字段定义。切换角色/用户组/人员时必须重新查询该目标绑定 codes，并用“绑定 codes ∩ 字段权限 option 定义”渲染列表。未选择授权目标时字段列表为空，保存按钮置灰。

**交互要求**：展示字段中文名、字段编码、安全要求标签（HIDDEN 红/MASKED 橙/PLAIN 绿）、当前授权目标访问级别（单选组）；支持批量设置同一数据表下字段权限。`NONE` 是可选、可保存的显式访问级别，不是空值。缺少绑定记录表示采用安全要求默认值（PLAIN/MASKED→READ，HIDDEN→NONE），不能表达“无权限”。

**添加字段**：点击“添加字段”时，从数据表/字段目录中选择字段；后端幂等 ensure 字段权限 option 定义（已存在则复用，不重复插入；不存在则按目录 `security_requirement` 生成完整 option 集）。创建成功后，前端立即把该字段的默认 access level code 加入当前授权目标的待保存选择，使字段立刻出现在列表；仅在点击“保存字段权限”后持久化绑定。刷新字段定义 options 时不得重新查询当前主体绑定并覆盖未保存选择。

**删除/编辑语义**：字段访问级别单选和“保存字段权限”只更新当前授权目标绑定。字段“编辑”只允许修改字段业务名等本地展示信息，`security_requirement` 以标签只读展示。字段“删除”是全局删除字段权限定义，会删除该字段全部 access_level option 并清理所有角色/用户组绑定，必须用危险按钮和二次确认文案明确提示“删除该字段及其所有权限配置”。

**验收**：读接口响应已隐藏或脱敏无权字段；写接口对无写权限字段拒绝或剔除并可审计；前端绕过控件直接提交不能生效。

### 7. 数据权限

**路由建议**：`/rbac/data-permissions`

数据权限页是 AuthzCraft 回路 2 的业务化配置入口。前端必须调用 AuthzCraft 数据权限接口或业务侧代理接口，规则不得保存到回路 1 RBAC 表。五项模板的后端编译规则见 [`data-permission-template-ast-spec.md`](./data-permission-template-ast-spec.md)。

#### 数据权限列表

列表（授权目标视角/数据表视角）展示已保存的数据权限规则，列定义：

| 列 | 来源 | 说明 |
|---|---|---|
| 授权目标类型 | 授权主体的 `principalKind` | 角色 / 用户组 / 用户 / 部门 / 岗位 |
| 授权目标 | 授权主体 `displayName`/`principalKey` | 业务名称 |
| 数据表（仅授权目标视角） | 策略 `targetRelationId` → 资源 `displayName` | 业务名称 |
| 数据规则名称 | 策略 `displayName` | 由后端按"模板 - 表 - 字段"生成 |
| 数据规则模板 | 策略 ACTIVE 修订关联的**规则蓝图 `display_name`**（`ruleBlueprintDisplayName`） | 取自 `authzcraft_rule_blueprint`，不是前端硬编码或解析 displayName |
| 状态 | 授权 `lifecycleState` | 生效/已禁用/已作废 |
| 操作 | — | 修改/禁用/作废 |

**不展示**"规则摘要"（与数据规则名称重复）、"失效时间"（长期生效规则该列恒为空）等冗余列；失效时间等次要信息放编辑抽屉。列表必须按当前选中的授权目标过滤（未选目标时显示全部供浏览）。

#### 页面术语

面向业务管理员的主标签必须使用以下定稿术语：

| 原建模术语 | 页面主文案 |
|---|---|
| 授权主体类型 | 授权目标类型 |
| 授权对象 | 授权目标 |
| 业务资源 | 数据表 |
| 数据权限模板 | 可见数据范围 |
| 规则模板 | 规则模板 |
| 锚点位置 | 数据归属字段来源 |
| 当前资源本人/归属人锚点字段 | 数据归属字段 |
| 关联资源本人/归属人锚点字段 | 数据归属字段 |
| 关联资源 | 关联表 |
| 失效时间 | 失效时间 |
| 保存后验证访问人 | 不在主表单展示；测试区如保留则用“测试人员” |

技术键如 `resourceKey`、`fieldKey`、`accessPathKey`、`operationCode` 只能作为辅助小字、调试信息或内部提交字段，不得作为主配置文案。

#### 标签有效性

表单 label、标题和提示文案必须提供新增信息，禁止重复控件已经表达的语义。若控件选项已经能说明选择含义，应省略局部 label 或用更高层级分组承载上下文。

| 场景 | 禁止设计 | 推荐设计 |
|---|---|---|
| 授权目标类型 | 在 `角色 / 用户组 / 人员` 分段控件上方再显示 `授权目标类型` | 分组标题使用 `授权给谁`，分段控件直接展示 `角色 / 用户组 / 人员` |
| 可见数据范围 | 卡片标题或区域标题已是 `可见数据范围`，控件上方再重复同义标签 | 直接展示 `全部数据 / 我的数据 / 我管理部门的数据 / 指定部门数据 / 分享...` 选项 |
| 数据归属字段来源 | 在 `本表 / 关联表` 控件上方写重复解释 | 直接展示 `本表 / 关联表`，必要时在后续字段区体现差异 |
| 数据归属字段 | 如果当前上下文只剩一个字段选择，不再追加说明性废话 | label 保留为 `数据归属字段`，placeholder/辅助文字只说明筛选规则或示例 |

有效 label 必须满足至少一项：说明需要输入的值、提供约束/单位、区分同屏多个相似控件、或提示业务后果。仅复述控件选项、分组标题、按钮动作或页面标题的 label 视为无效解释信息，必须删除。

#### 向导步骤

1. **选择授权目标**：角色、用户组或人员。展示业务名称，技术键只作为辅助信息。
2. **选择数据表**：展示表名称、业务说明、支持的操作。资源来自 AuthzCraft 资源接口或业务侧代理接口。
3. **选择可见数据范围**：全部数据、我的数据、我管理部门的数据、指定部门数据、分享某人的数据权限给某人。
4. **填写模板参数**：只展示当前模板必需参数；数据归属字段来源必须支持“本表”和“关联表”。
5. **预览影响范围**：展示策略摘要、授权目标、数据表、操作、有效期、风险提示。
6. **保存并回显**：保存后展示策略 ID/授权 ID、状态、审计入口。

#### 模板 0：全部数据

**默认值**：无需数据归属字段、部门范围、归属人等参数，选择此模板时隐藏数据归属字段来源、关联表、数据归属字段等配置项。

**必填项**：数据表、操作范围。

**可选项**：有效期、备注。

**文案示例**：`允许该角色查看全部客户数据`。

**冲突提示**：全部数据会覆盖同主体同资源的其它数据范围规则，保存前必须提示“该规则将覆盖同主体的其它数据范围规则”。

#### 模板 1：我的数据

**默认值**：优先推荐负责人、创建人、销售、申请人等候选数据归属字段。

**必填项**：数据表、操作范围、数据归属字段。

**可选项**：有效期、备注。

**文案示例**：`允许该角色查看负责人是本人的商机数据`。

**禁止**：要求业务人员填写 SQL 条件或 PIP 参数名。

**关联表字段**：当“我的数据”需要通过明细表判断时，必须允许选择关联表和数据归属字段。例如会议数据表选择“会议参会人”表后，以其中的“参会人账号”作为数据归属字段，表达“我参与的会议”。`accessPathKey` 只作为内部映射值，不作为业务人员主要选项展示。

#### 模板 2：我管理部门的数据

**默认值**：默认勾选直接管理部门。

**必填项**：数据表、操作范围、数据归属字段、部门范围。

**部门范围**：直接管理部门、管理的下级部门、分管的部门，支持多选。

**下级层级**：当勾选“管理的下级部门”时必须出现层级选择，支持至少 1 级、2 级、3 级、全部下级。

**文案示例**：`允许该角色查看本人直接管理部门及 2 级下级部门的客户数据`。

#### 模板 3：指定部门数据

**默认值**：不预选任何部门，需业务人员主动指定。

**必填项**：数据表、操作范围、数据归属字段、至少一个部门编码。

**部门编码**：支持多选/多值输入，直接指定字面部门编码，不经过管理层级推导，与“我管理部门的数据”模板互斥使用。

**文案示例**：`允许该角色查看所属部门属于指定部门（D001、D002）的客户数据`。

#### 模板 4：分享某人的数据权限给某人

**默认值**：默认需要有效期或提供明确撤销入口。

**必填项**：数据归属人、被分享人、数据表、操作范围。

**可选项**：有效期、分享原因、是否允许再次分享。

**操作**：创建分享、查看分享、撤销分享、查看审计。

**文案示例**：`将张三负责的客户数据查看权限分享给李四，有效期至 2026-12-31`。

## 四、API 调用清单

字段级请求/响应契约见 [`authzcraft-rbac-api-contract.md`](./authzcraft-rbac-api-contract.md)。实现前端 API client 前必须先对照该契约；若目标后端字段不同，必须显式编写 adapter 映射，不得让页面组件直接依赖不稳定字段。

具体路径可按目标系统代理层调整，但语义必须完整：

| 能力 | 推荐 API 语义 |
|---|---|
| 查询角色 | `POST /authzcraft/api/v1/principals/roles/search` |
| 创建/更新角色 | `POST /authzcraft/api/v1/principals/roles` |
| 退休角色 | `POST /authzcraft/api/v1/principals/roles/{roleCode}/retire` |
| 查询用户组 | `POST /authzcraft/api/v1/principals/groups/search` |
| 创建/更新用户组 | `POST /authzcraft/api/v1/principals/groups` |
| 退休用户组 | `POST /authzcraft/api/v1/principals/groups/{groupCode}/retire` |
| 查询成员关系 | `POST /authzcraft/api/v1/principals/memberships/search` |
| 创建/更新成员关系 | `POST /authzcraft/api/v1/principals/memberships` |
| 关闭成员关系 | `POST /authzcraft/api/v1/principals/memberships/close` |
| 查询用户/组织/岗位 | `POST /authzcraft/api/v1/principals/users/search`、`/organizations/search`、`/positions/search` |
| 查询当前用户权限 | 目标业务系统当前用户权限接口，返回 `permissions` 和 `fieldPermissions` |
| 保存功能授权 | 目标业务系统角色-权限接口，保存 `roleCode -> permissionCode[]` |
| 保存字段授权 | 目标业务系统角色-字段权限接口，保存 `roleCode -> fieldPermission[]` |
| 查询数据资源 | AuthzCraft 回路 2 资源查询接口或业务侧代理接口 |
| 保存数据权限规则 | AuthzCraft 回路 2 策略/授权接口或业务侧代理接口 |
| 查询审计 | AuthzCraft 审计查询接口或业务侧代理接口 |

若任一 API 未就绪，必须在交付结果中列出缺口、建议路径、请求/响应字段草案和临时不可验收项。

## 五、状态处理

每个页面必须覆盖以下状态：

- 加载中：骨架屏或表格 loading。
- 空数据：提供下一步动作，如“创建角色”“添加成员”。
- 无权限：隐藏不可见入口；直接访问路由显示 403 或无权限提示。
- 保存中：按钮 loading，禁止重复提交。
- 部分成功：展示成功数、失败数和失败明细。
- 接口失败：展示可理解错误信息，并保留用户已填内容。
- 只读模式：无管理权限时可查看但不可编辑。

## 六、验收用例

完整验收必须对照 [`rbac-frontend-acceptance-checklist.md`](./rbac-frontend-acceptance-checklist.md) 执行；本节只列出最小冒烟用例。

1. 新建角色后，角色列表出现该角色，默认无高风险权限。
2. 从人员维度一次给 3 个人分配 2 个角色，保存前能看到新增关系，保存后成员关系可查。
3. 从角色维度批量移除成员，保存前能看到移除名单，清空成员需要二次确认。
4. 给角色授权一个按钮权限后，拥有该角色的用户能看到按钮；移除授权后按钮隐藏，直接请求后端返回 403。
5. 字段设置为 `HIDDEN` 后，读响应不返回该字段或返回受控空值；直接提交该字段不能写入。
6. 使用“我的数据”模板保存规则，业务人员只选择数据表、数据归属字段和操作范围，不填写 SQL 或策略 DSL。
7. 使用“我管理部门的数据”模板时，可复选直接管理部门、管理的下级部门、分管的部门；勾选下级部门后可指定层级。
8. 对根数据表使用关联表字段时，可选择关联表和该表字段，保存后后端根据内部 access path 映射生成 `EXISTS_PATH`，例如按参会人明细判断“我参与的会议”。
9. 使用“指定部门数据”模板时，可指定一个或多个部门编码；至少指定一个才能保存。
10. 使用“分享某人的数据权限给某人”模板后，可查询分享记录并撤销。
11. 数据权限规则保存后可在 AuthzCraft 回路 2 查询或审计，业务列表数据由后端 PEP 决定返回范围，前端不自行过滤。
