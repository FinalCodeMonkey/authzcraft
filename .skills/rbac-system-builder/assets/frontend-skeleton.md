# RBAC 前端管理页骨架

> 技术栈无关：按目标前端框架（Vue / React / Angular 等）落地。
> 核心原则：**菜单/按钮的隐藏必须基于后端返回的权限点，禁止前端写死**。
> 改造既有前端时，优先接入现有登录态、API 客户端、路由和组件库，禁止引入第二套用户体系。
> 详细页面规格、API 语义、状态处理和验收用例见 [`frontend-rbac-page-spec.md`](./frontend-rbac-page-spec.md)。
> 字段级请求/响应契约见 [`authzcraft-rbac-api-contract.md`](./authzcraft-rbac-api-contract.md)。

## 二、核心功能

前端交互必须符合 RBAC 权限管理最佳实践：以角色、用户组、人员、权限、数据范围为核心对象组织页面；列表用于查找，详情抽屉用于编辑，树表/矩阵用于授权，穿梭选择器或批量选择面板用于成员分配。所有批量变更必须提供已选数量、变更差异预览、冲突/重复提示、保存结果反馈和失败项明细。

### 1. 角色与用户组管理页

- 角色列表（分页）
- 创建、编辑角色
- 删除角色（**必须确认弹窗**，展示影响范围）
- 用户组列表（分页）
- 创建、编辑用户组
- 删除/退休用户组（**必须确认弹窗**，展示影响范围）
- 真实调用 AuthzCraft 主体接口或业务侧代理接口，不得以静态 mock 作为最终实现

### 2. 双向批量成员分配页

- **按人员分配**：选择一个或多个人员后，批量分配角色或用户组
- **按角色/用户组分配**：进入角色或用户组详情后，批量添加或移除人员
- 支持人员搜索、角色/用户组搜索、分页、已选去重、已有关联回显、增量添加、批量移除
- 移除成员、清空成员等高风险操作必须有确认弹窗
- 用户、组织、岗位、角色、用户组 ID 必须保持字符串，不得使用 `Number()`、`parseInt()` 或一元 `+` 转换
- 批量保存前必须展示新增、保留、移除的差异，避免管理员误清空或重复授权

### 3. 功能授权管理页

- 展示权限点树/列表
- **分组维度对齐业务导航心智**：权限分组 MUST 与前端菜单/导航/业务域对齐，而不是后端技术维度（资源表、表名、API 分组）。具体分组键由探查目标业务确定。
- **面向人的文案与面向机器的标识分离**：操作权限 checkbox 只显示业务名称（如"查看报销单"），不拼接技术标识（权限 URN、code、resourceKey）。`name · code` 视为反例。
- 给角色或用户组批量勾选/取消勾选权限点，支持全选/半选、搜索过滤、变更预览和保存结果反馈
- 保存时角色调用后端 `POST /api/rbac/roles/{roleCode}/permissions/replace`，用户组调用 `POST /api/rbac/groups/{groupCode}/permissions/replace`；即使启用 `LOCAL`，前端也应以稳定 `roleCode/groupCode` 作为功能/字段授权绑定键，不使用本地 `role_id/group_id` 作为授权接口主键。
- 权限点编码必须与后端 `permissionCode` 逐字一致
- 优先采用"权限资源树 + 角色列/操作列"的矩阵或树表形态，支持按模块折叠、搜索定位、只看已授权和半选态

### 4. 字段授权页（两维模型）

- 字段权限采用两维模型：`security_requirement`（字段固有属性，PLAIN/MASKED/HIDDEN）× `access_level`（授权可变属性，NONE/READ/PLAIN_READ/WRITE）
- `security_requirement` 是字段固有属性，权威来源是 AuthzCraft 回路 2 字段目录；RBAC 前端不得创建/编辑该值，只展示安全要求标签
- 角色/用户组授权时只选 `access_level`（单选，含"无权限"档），`security_requirement` 由字段决定不可变
- 字段权限 tab 只显示当前授权目标已绑定或本次待保存绑定的字段；未选授权目标时列表为空，保存按钮置灰
- 点击“添加字段”时选择数据表和字段，后端幂等 ensure 字段权限 option 定义；前端把默认 access level code 加入当前授权目标待保存集合并立即显示，点击“保存字段权限”后才持久化
- `NONE` 是显式可保存 access_level；删除绑定只表示回退默认访问级别，不能当作无权限
- 字段权限来源于后端返回的 `fieldPermissions`（数组，每项含 `securityRequirement` 和 `accessLevel`）
- 字段权限最终由后端执行，前端只做展示、只读、脱敏提示和提交前剔除等交互控制
- 安全要求用标签颜色区分（HIDDEN 红/MASKED 橙/PLAIN 绿）

### 5. 数据权限配置页（AuthzCraft 回路 2）

数据权限配置页是 AuthzCraft 回路 2 的业务化配置入口，可以放在 RBAC 管理区，但规则必须保存到 AuthzCraft 数据权限后端，不得写入回路 1 RBAC 表，也不得让前端过滤业务行数据。

必须支持以下业务规则模板：

| 规则模板 | 前端配置能力 | 后端落地 |
|---|---|---|
| 全部数据 | 选择数据表和操作范围，无需指定数据归属字段 | 编译为 `{"operator":"TRUE"}` 谓词，simulation 期望 `ALLOW_ALL`；会覆盖同主体同资源的其它规则，保存前必须提示 |
| 我的数据 | 选择数据表和数据归属字段，如负责人、创建人、销售等 | 映射为 AuthzCraft 行过滤策略模板 |
| 我管理部门的数据 | 部门范围复选：直接管理部门、管理的下级部门、分管的部门；下级部门可指定几级 | 生成策略参数，部门关系由 AuthzCraft/PIP 解析 |
| 指定部门数据 | 直接多选一个或多个部门编码，不做管理层级推导 | 生成按部门编码集合过滤的 `IN` 策略参数，部门编码作为授权参数直接落地 |
| 分享某人的数据权限给某人 | 选择授权人、被分享人、数据表、失效时间/状态、可访问操作 | 保存为 AuthzCraft 授权绑定或等价分享策略，支持撤销和审计 |

页面必须提供资源选择、策略预览、影响范围提示、保存前确认、保存后回显、错误信息展示、禁用状态处理和审计入口。若 AuthzCraft 数据权限后端接口未就绪，必须输出接口缺口清单，不得伪造成已完成。

五项通用数据权限场景必须简单易用，优先采用模板向导：

1. 选择授权目标：角色、用户组或人员
2. 选择数据表：用业务名称展示表，技术键只作为辅助信息
3. 选择可见数据范围：全部数据、我的数据、我管理部门的数据、指定部门数据、分享某人的数据权限给某人
4. 选择数据归属字段来源（本表或关联表）和数据归属字段，填写必要参数并预览影响范围

默认值必须贴近日常业务：我的数据默认推荐负责人/创建人等数据归属字段；我管理部门的数据默认勾选直接管理部门，并允许追加管理的下级部门层级、分管部门；指定部门数据默认不预选任何部门，需业务人员至少指定一个；分享规则默认要求失效时间或撤销入口。页面文案必须使用业务语言，禁止把底层策略 DSL、SQL、PIP 参数名或内部主键作为业务人员的主要配置项。

页面主标签必须采用定稿术语：授权目标类型、授权目标、数据表、可见数据范围、规则模板、数据归属字段来源、关联表、数据归属字段、失效时间。不得把“授权主体类型”“授权对象”“业务资源”“数据权限模板”“锚点位置”“锚点字段”“关联资源”作为主标签；“保存后验证访问人”不得出现在主配置表单中，测试入口如保留必须独立命名为“测试人员”。

同时必须避免无效解释标签：控件选项、分组标题或页面标题已经表达含义时，不得再放一个重复 label。分段控件/Tab 尤其要注意，例如 `角色 / 用户组 / 人员` 前不再显示 `授权目标类型`，`本表 / 关联表` 前不再显示重复解释，`我的数据 / 我管理部门的数据 / 指定部门数据` 前不再重复同义说明。需要上下文时优先使用短分组标题（如 `授权给谁`、`控制哪些数据`），而不是给每个自解释控件都加 label。辅助说明只能解释业务后果、限制条件或示例，不得复述选项文字。

当数据范围需要通过明细/关联表判断时，页面必须提供“数据归属字段来源 = 关联表”的配置：选择业务人员能理解的关联表，再选择该表的数据归属字段，预览文案以业务语言说明“通过某关联表判断”。`accessPathKey` 只在前端内部由关联表映射得到并提交给后端，禁止作为主要选项展示，也禁止让业务人员填写 SQL join、子查询或底层 AST。

### 6. 权限控制（菜单/按钮级）

- **菜单级**：路由守卫根据权限点判断是否可访问
- **按钮级**：`v-permission` 指令根据权限点判断是否显示
- **字段级**：根据后端返回的字段权限控制显示、只读或脱敏

前端只负责回路 1 的交互控制；行数据过滤属于 AuthzCraft 回路 2，必须在后端数据 PEP 执行。前端不得根据角色、部门或用户自行过滤业务行数据。

## 三、权限控制实现（核心）

### 登录后获取权限点

```
// 登录成功后，从后端获取当前用户权限点集合
authzState = await authApi.getCurrentUserPermissions()
permissions = authzState.permissions
fieldPermissions = authzState.fieldPermissions
requestKey = authzState.requestKey
// permissions 存入 store：['app:user:create', 'app:user:read', 'app:role:read', ...]
// fieldPermissions 存入 store：[{ resourceKey, fieldKey, accessLevel, securityRequirement }]
//   其中 accessLevel ∈ NONE/READ/PLAIN_READ/WRITE，securityRequirement ∈ PLAIN/MASKED/HIDDEN（字段固有属性）
```

### 菜单级控制（路由守卫）

```
router.beforeEach((to, from, next) => {
    if (to.meta.requiredPermission && !hasPermission(to.meta.requiredPermission)) {
        next('/403')   // 无权限跳转 403
    } else {
        next()
    }
})
```

### 按钮级控制（v-permission 指令）

```
// 指令：无权限时移除元素
Vue.directive('permission', {
    mounted(el, binding) {
        if (!hasPermission(binding.value)) {
            el.parentNode.removeChild(el)
        }
    }
})

// 使用
<button v-permission="'user:delete'">删除用户</button>
```

### 字段级控制

```
fieldPermission = getFieldPermission(resourceKey, fieldKey)
if fieldPermission.securityRequirement == 'HIDDEN': 不渲染字段
if fieldPermission.accessLevel == 'READ' && securityRequirement == 'MASKED': 展示后端返回的脱敏值
if fieldPermission.accessLevel == 'READ' && securityRequirement == 'PLAIN': 展示原值，禁止编辑
if fieldPermission.accessLevel == 'PLAIN_READ': 展示原值，禁止编辑
if fieldPermission.accessLevel == 'WRITE': 允许编辑
if fieldPermission.accessLevel == 'NONE': 不渲染字段，提交时剔除
```

字段权限只是交互控制；读响应中的隐藏/脱敏和写入校验必须由后端真实执行。前端即使禁用或剔除字段，也不能作为权限生效依据。

## 四、硬约束

1. **菜单/按钮隐藏必须基于后端返回的权限点**：禁止前端写死 `if (user.role === 'admin')`。
2. **权限点编码逐字一致**：前端 `v-permission="'user:delete'"` 的编码必须与 DDL 权限表、后端拦截器完全一致。
3. **删除角色、移除成员必须有确认弹窗**：展示影响范围，用户确认后才调用后端。
4. **前端隐藏 ≠ 后端放行**：前端隐藏只是 UX，真正的权限校验在后端拦截器，禁止只做前端隐藏不做后端校验。
5. **前端行过滤禁止**：列表数据必须来自后端已授权结果；禁止前端用角色、部门、用户 ID 再过滤业务行。
6. **字段权限来源**：字段显示/编辑控制必须来自后端当前用户权限点或字段权限配置，禁止前端写死角色判断。
7. **字段权限不是前端安全边界**：前端必须假设用户可以绕过 UI 直接构造请求；后端必须对响应字段和提交字段做真实校验。
8. **AuthzCraft 接口真实调用**：角色、用户组、成员关系、数据权限配置必须真实调用 AuthzCraft 接口或业务侧代理接口，禁止 mock-only 完成交付。
9. **ID 精度保护**：用户、组织、岗位、角色、用户组 ID 均按字符串传递，禁止 `Number()`、`parseInt()` 或一元 `+`。
10. **业务化配置**：数据权限配置必须通过模板、选择器、预览和业务化文案完成，禁止要求业务人员直接理解底层策略表达式。
11. **既有演示页面保护**：给演示页面增加回路 1 权限控制时，不得删除或绕过原本用于回路 2 验证的 simulation、真实查询、PEP Header 和 audit 查询链路。

## 五、验证标准

| 验证项 | 标准 |
|---|---|
| 无权限菜单 | 真实隐藏/不可访问 |
| 无权限按钮 | 真实隐藏 |
| 权限点编码 | 与 DDL、后端逐字一致 |
| 删除角色 | 有确认弹窗 |
| 用户组管理 | 能创建/编辑/删除或退休用户组，真实调用 AuthzCraft 或业务侧代理接口 |
| 成员批量分配 | 支持人员维度批量分配角色/用户组，也支持角色/用户组维度批量添加人员 |
| 批量变更预览 | 保存前展示新增、保留、移除差异，保存后展示成功和失败明细 |
| 功能授权 | 角色授权保存后，运行时菜单、按钮、API 权限真实生效 |
| 前端隐藏 | 后端仍有校验（非只做前端） |
| 字段权限 | 后端响应已隐藏/脱敏无权字段，直接提交无权字段不能写入；业务查询 SQL 查出全部字段，字段投影从 `field_permissions` 表配置驱动，不硬编码受控字段列表 |
| 数据权限配置 | “我的数据”“我管理部门的数据”“指定部门数据”“分享某人的数据权限给某人”可保存到 AuthzCraft 回路 2 并可查询/审计 |
| 易用性 | 五项通用数据权限通过模板向导配置；关联字段场景通过关联表 + 字段选择完成，业务人员不需要填写 access path、底层策略 DSL、SQL 或 PIP 参数 |
| 行数据 | 前端不自行过滤，后端数据 PEP 决定返回范围 |
| 回路 2 演示 | 新增回路 1 控制后，原有 simulation/真实查询/audit 验证仍可运行 |

## 六、UE 交互设计规范

以下规范归纳自 demo-oa 权限管理模块的 UE 实践，改造其它项目时 MUST 遵循。

**注意：`当前访问人切换器`（演示用 personaKey 下拉）是权限演示专用机制，不适用于通用业务系统改造，不作为规范纳入；改造其它项目时不应生成该控件。**

### 6.1 菜单要求

| 要求 | 说明 |
|---|---|
| 分组语义化 | 左侧导航按业务域分组，权限管理子菜单顺序固定：角色 → 用户组 → 成员 → 授权 |
| 菜单按权限显隐 | 菜单可见性由后端权限点驱动，前端不写死角色判断 |
| 两级权限门禁 | "看"用 read 权限控制菜单入口可见，"管"用 manage 权限控制页面内写操作可用，二者独立授权 |
| 选中态清晰 | 当前菜单高亮，子菜单键统一，路由与菜单键一一对应 |

### 6.2 功能要求

| 能力 | 要求 |
|---|---|
| 列表页 | 统一"搜索 + 表格 + 操作列"；操作列用链接式按钮密集排列 |
| 详情/编辑 | 轻量表单用 Modal，复杂配置用 Drawer（字段多 + 含向导） |
| 授权配置 | 功能权限用树表 + 折叠 + 全选/半选/反选；字段权限用折叠矩阵 + 单选（含"无权限"档）；数据权限用"列表优先 + 抽屉 + 双视角 + 模板向导" |
| 成员分配 | **必须双向**：人 → 角色/用户组、角色/用户组 → 人，两入口均支持批量 |
| 差异预览 | 保存前展示"新增/移除/保留"差异计数；批量分配展示成功数 + 失败明细表 |
| 状态覆盖 | 加载中、空态、部分成功、失败明细、只读态缺一不可 |
| 权限画像 | 从"人"视角可查某用户的全部角色/用户组/权限归属，便于审计核对 |

### 6.3 布局与交互建议

| 维度 | 建议 |
|---|---|
| 布局范式 | 列表优先，配置下沉到抽屉/弹窗；数据权限列表支持双视图切换（Segmented） |
| 高风险防护 | 删除/停用/作废/清空成员/批量移除必须二次确认（Popconfirm），确认文案动态带数量与影响范围 |
| 状态分态处理 | 数据规则生命周期"禁用/启用/作废"三态分离，作废不可逆、禁用可逆，按钮随状态显隐 |
| 影响预警 | 不可逆或影响面大的操作用 `a-alert` 前置警告 |
| 技术键降噪 | 主文案走业务语言；技术键仅在需区分同名主体时作辅助，不作为主选项 |
| 权限表现分层 | 菜单级隐藏 + 按钮级禁用 + 字段级标签（红/橙/绿表安全等级）三层，均源自后端权限返回值 |

**核心主线**：列表优先、配置下沉、批量操作为王、差异可预览、高风险必确认、状态全覆盖、权限分层控制、技术键降噪。
